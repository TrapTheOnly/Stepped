# 2026-03-25 Session

## Decisions

### Wishlist creation and AI/manual editors refreshed
**What:** Replaced the old Wishlist add dialog with a dedicated title-only add screen, refreshed the AI/manual editor shells to the frosted Wishlist design system, and added purpose-aware AI planning plus root cover-image storage.
**Why:** The old creation and planning flows still used dialog/admin-style layouts, did not bind cloud credits to the authenticated user, and stored request-only drafts in a way that could be mistaken for a real saved itinerary.
**Impact:** Wishlist creation now branches cleanly into AI review or manual editing, AI requests carry authenticated credits plus trip purpose, generated plans persist a root cover image, and request-only drafts no longer inflate readiness or masquerade as saved itineraries.


### Wishlist AI flow uses request-only drafts safely
**What:** Wishlist AI planning now supports saving request-only drafts with purpose metadata, while parsing/readiness logic only treats a draft as a real itinerary when summary/duration/time windows/city plan data exists.
**Why:** The new title-first add flow and refreshed AI editor needed to save country/timing/purpose preferences before generation, but the previous parser/readiness checks treated any JSON payload as a saved plan.
**Impact:** AI draft preferences persist cleanly across Wishlist flows without showing a false saved itinerary on cards or plan review.

<details>
Context: The Wishlist add flow now creates an item before AI generation and the AI editor can save draft preferences, including trip purpose and timing, before an itinerary exists. Options considered: 1) avoid storing draft request metadata until after generation, which would lose user inputs between screens; 2) store request metadata inside aiPlan and teach the parser/UI to distinguish request-only payloads from real itineraries. Decision: choose option 2. parseStoredGeminiPlan now returns null for request-only payloads, readiness uses a real-plan-data check instead of aiPlan non-empty, and saveWishlistPlanDraft always writes request metadata while preserving ui_state and cover metadata. Tradeoffs: aiPlan now mixes request metadata and itinerary metadata in one JSON blob, so helper functions must stay consistent about what counts as generated content. Follow-up: if backend starts returning richer cover metadata or usage stats, keep mergeWishlistPlanUiState in sync so manual saves do not drop those root-level fields.
</details>
