# 2026-03-24 Session

## Decisions

### Lock app to portrait orientation
**What:** Locked the Flutter app to portrait-only mode at startup and reinforced it on Android's main activity.
**Why:** The user wanted the app to stay vertical and never rotate horizontally. Applying the lock in main.dart covers runtime orientation, while the AndroidManifest setting keeps launch/activity behavior consistent on Android.
**Impact:** The app now stays in portrait on mobile, including Android launch, without affecting the rest of the UI.

<details>
Context:
The user requested that the app only work in vertical layout and not rotate horizontally.

Options considered:
- Lock orientation only in Flutter via SystemChrome.setPreferredOrientations.
- Lock orientation in Flutter and also enforce portrait on Android's MainActivity.

Decision:
Implemented both. main.dart now sets preferred orientations to DeviceOrientation.portraitUp before app startup, and AndroidManifest.xml sets android:screenOrientation="portrait" on MainActivity.

Tradeoffs:
This intentionally prevents landscape use on mobile. Desktop behavior is unchanged because device orientation is primarily relevant on mobile.

Follow-up:
If needed later, iOS native supported orientations can also be narrowed in Info.plist, but the Flutter runtime lock already covers app behavior.
</details>


### Wishlist plan review uses shared hero image source
**What:** Updated Wishlist plan review to reuse the wishlist item's primary image source from stored AI city-card data, fall back to a blank atmospheric placeholder instead of random imagery, move empty-state actions into a sticky frosted bottom dock, and replace the text-heavy saved itinerary layout with card-based overview, season, and route sections.
**Why:** The user wanted the review page to visually match the refreshed wishlist cards, avoid duplicated titles/icons and mismatched random images, and make both the empty state and saved itinerary feel lighter and more intentional.
**Impact:** Wishlist plan review now shares imagery with the wishlist card when possible, avoids overlay bugs in blank states, presents AI/manual creation actions as bottom-docked controls, and shows saved itineraries with cleaner overview, season-note pills, and expandable city cards.

<details>
Context:
The wishlist plan review redesign had visual issues after the first pass: duplicated title text in the hero when no image was available, a mismatched/random hero image compared with the wishlist card, empty-state buttons embedded inside a content card instead of behaving like floating dock actions, and saved itinerary sections that still felt too text-heavy and repetitive.

Options considered:
- Keep separate image-selection logic for the wishlist card and review page.
- Reuse the first AI city-card image everywhere and show a blank atmospheric fallback when no image exists.
- Keep the empty-state call-to-action buttons inline in the scroll content.
- Move the empty-state actions to a frosted bottom dock so they behave more like app chrome.
- Retain the old stat cards for trip length, city count, and time windows.
- Remove duplicate stat cards and move the useful duration rationale into the overview area.

Decision:
Use a shared helper to derive the primary wishlist image from stored AI plan city-card data, return null when no image exists, and let both the wishlist card and plan review hero use that source. Replace the old random fallback art with blank atmospheric placeholders that contain no duplicate title/icon text. In the empty state, mount Generate with AI and Create manually into a sticky frosted bottom dock layered by the review shell. For saved plans, simplify the page into a hero, overview with duration rationale, season notes with month pills, and expandable image-led city route cards.

Tradeoffs:
The blank fallback is less visually rich than a random stock photo, but it prevents visual mismatch and preserves trust in the destination imagery. Parsing the stored AI plan for image selection couples the hero to AI-plan data shape, but it keeps the visuals consistent across wishlist and review surfaces.

Follow-up:
If the AI plan schema changes, update wishlistPrimaryImageUrl accordingly. The AI plan editor still uses the older design system and can be refreshed in a later pass.
</details>

### Wishlist city guides and save refresh flow
**What:** Refined Wishlist plan review with a clearer readiness explainer, compact top-bar action layout, and route cards that open a dedicated city guide screen. Also fixed the AI/manual edit return flow by invalidating cached wishlist item providers after saves and added a city-level checkable things-to-do state persisted inside aiPlan ui_state metadata.
**Why:** The review page needed less crowded top-bar actions, a clearer explanation of readiness, and route cards that matched their affordance by opening a separate page. The AI editor already wrote plans to the database, but the cached FutureProvider made review data appear stale until app restart, so explicit invalidation was required.
**Impact:** Wishlist plan review now refreshes immediately after AI generation or manual edits, city cards open a dedicated detail screen with a fresher itinerary layout, and city checklist progress survives later AI/manual plan rewrites because extra ui_state is preserved when saving aiPlan payloads.

<details>
Context:
The user wanted three connected wishlist improvements after the plan review redesign: tighten the top-bar icon spacing, make AI-generated plans immediately visible when returning from the AI editor, and move per-city route details into a dedicated city page with a more purposeful itinerary design and a checkable things-to-do list.

Options considered:
- Keep the review page as one long scroll and continue expanding city cards inline.
- Turn route cards into true navigation cards and move the richer city experience into a dedicated screen.
- Keep readiness scoring opaque on the card only.
- Surface the readiness breakdown on the plan review page so the user can see what is still missing.
- Store checklist state outside aiPlan.
- Persist checklist state as extra ui_state metadata inside aiPlan and preserve it across future AI/manual saves.

Decision:
Use a dedicated WishlistPlanCityDetailScreen for route details, keep the review page focused on overview + season + entry cards, add a readiness card driven by a user-facing four-step scoring model, and preserve city checklist progress via aiPlan ui_state merged back into generated/manual payloads. Also invalidate wishlistItemProvider and wishlistStreamProvider after AI generation, explicit draft save, and manual save.

Tradeoffs:
The city edit button currently routes into the existing manual plan editor rather than a fully city-scoped edit form, which keeps implementation time reasonable while still making edits available. Persisting checklist progress in aiPlan metadata adds a small amount of schema coupling, but the parser ignores unknown keys and the data survives rewrites.

Follow-up:
If a dedicated city edit flow is added later, it can read/write the same stored plan payload and checklist metadata. The readiness logic now lives in wishlist_editorial_widgets.dart and can be reused anywhere the app wants to explain score composition.
</details>

### Trips editor now matches wishlist overlay patterns
**What:** Reworked the trip add/edit flow to use a positioned frosted top bar and floating bottom dock button, removed manual cover-image URL entry, and expanded trip city data so cities can store uploaded images plus manual itinerary content alongside inherited wishlist itinerary.
**Why:** The user wanted the trip editor to stop using the plain scaffold shell, remove the duplicate page title and bottom strip behind Update Trip, avoid SSRF-prone cover image URLs, fix the city screen top-bar overlay bug, and make trip city pages show the same kind of itinerary structure as Wishlist while still working for manual trips.
**Impact:** Trips add/edit now has a single large top-bar title, a semi-translucent floating Update Trip button styled like Wishlist's highlighted dock buttons, upload-only cover media controls, city cards that reflect itinerary availability, and a city detail screen that supports uploaded city photos, editable itinerary stops, editable things-to-do, ratings, visited places, and inherited wishlist itinerary context.

<details>
Context:
The user requested a coordinated cleanup of the Trips edit/view flow after Wishlist had already been stabilized. They wanted the city detail page to stop suffering from the same full-screen top-bar overlay issue, the trip editor to stop showing both a top-bar title and an in-page Edit trip heading, the Update Trip call-to-action to match Wishlist's floating highlighted dock button treatment, the trip media section to remove manual URL entry for security reasons, and trip city pages to expose itinerary content in the same style as Wishlist while still supporting manual trips.

Options considered:
- Patch the existing plain AppBar/bottomNavigationBar trip editor and leave the city page mostly as-is.
- Move the trip editor and trip city page back onto the proven Wishlist-style overlay pattern and extend trip city persistence to hold manual itinerary data and city images.

Decision:
Used the second approach. AddTripScreen now renders inside a positioned overlay shell with a frosted top bar and floating dock button. AddTripMediaNotesSection now only supports upload/clear controls while preserving preview behavior. TripCityEntry gained persisted imageUri, itineraryOverview, itineraryStops, and suggestedPlaces fields. TripCityDetailScreen now seeds those fields from inherited wishlist data when available, lets the user upload a city photo, edit overview/day-flow/things-to-do, and save the result back into trip city JSON.

Tradeoffs:
The city editor now persists inherited itinerary into the trip city record when the user saves, which keeps the UI consistent and editable but duplicates some wishlist-derived content inside the trip record. That was acceptable here because it gives manual and inherited trips a single editable data shape.

Follow-up:
If the user wants the trip city screen to match Wishlist even more closely later, the remaining next step would be extracting shared city-guide shell components between Wishlist and Trips.
</details>

### Position Trips top bar as overlay
**What:** Changed the Trips page top bar from a non-positioned SafeArea child in an expand-fit Stack to an explicit Positioned top overlay, matching Wishlist.
**Why:** The non-positioned top bar layer in Trips could receive full-screen constraints after hot reload and behave like an invisible touch blocker. Matching Wishlist's Positioned overlay avoids that constraint issue while keeping the same visual layout.
**Impact:** Trips navigation and interactions should no longer be blocked by the frosted top bar layer after hot reload or rebuilds.

<details>
Context:
The user identified that Wishlist had already been fixed by moving its floating top bar to an explicitly positioned overlay. Trips still used Stack(fit: StackFit.expand) with the navbar added as a normal SafeArea child.

Options considered:
- Keep the current Trips structure and debug around pointer handling.
- Mirror the known-good Wishlist overlay pattern exactly.

Decision:
Updated TripsScreen so the SteppedTopBar sits inside Positioned(top: 0, left: 0, right: 0, child: SafeArea(...)) instead of being a non-positioned child of the expand-fit Stack.

Tradeoffs:
This is a narrow structural fix with minimal visual risk because Wishlist already uses the same pattern successfully.

Follow-up:
If a similar issue appears on other overlay screens, check for non-positioned full-width children inside StackFit.expand stacks and convert them to explicit Positioned overlays.
</details>
